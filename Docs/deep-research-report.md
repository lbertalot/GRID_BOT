# Protocolo de Investigación Técnica y Estratégica: Bot de Trading **“Passive Income” v1.0**

## 1. Filosofía de Inversión y Estrategia
- **Enfoque direccional:** Se priorizarán activos de alta capitalización (BTC, ETH, acciones líderes o Cedears), aprovechando tendencias claras del mercado. Se emplearán indicadores de *momentum* (por ejemplo, el **Indicador Momentum** anticipa cambios de tendencia y mide la velocidad del movimiento de precios【19†L305-L312】) junto con métricas de volatilidad (p.ej. bandas de Bollinger como medidor de volatilidad【21†L97-L100】).
- **Análisis técnico y cuantitativo:** Se integrarán indicadores técnicos (MACD, RSI, EMAs, etc.) con modelos cuantitativos basados en series temporales. Por ejemplo, **medias móviles exponenciales (EMA)**, que dan más peso a precios recientes y reaccionan rápido a cambios de mercado【21†L51-L54】, serán usadas para detectar cruces de tendencia. Estos elementos técnicos se combinan con análisis de series de precios históricos (p.ej. ARIMA o regresiones en streaming) para robustecer las señales.
- **Análisis de sentimiento:** Se aplicará *NLP* sobre fuentes de noticias y redes sociales para estimar el “humor del mercado”. El análisis de sentimiento codifica si predominan optimismo o miedo, anticipando movimientos antes de que los indicadores técnicos lo confirmen【18†L87-L95】. La literatura sugiere que los datos de sentimiento mejoran la precisión de las predicciones cuando se validan con indicadores tradicionales (p.ej. MACD, RSI)【18†L154-L160】. Al cruzar señales técnicas con la dirección del sentimiento (positivo/negativo), el bot obtendrá confirmaciones más sólidas antes de abrir posiciones.
- **Horizonte de trading:** Se balanceará el *day trading* (operaciones intradía) y el *swing trading* (varios días) para optimizar costos. El swing trading tiende a reducir la frecuencia de operaciones y, por tanto, las comisiones y el *slippage*, sacrificando algo de oportunidad de retorno inmediato【23†L255-L262】. De hecho, en swing trading se ha documentado que baja la carga operativa diaria y permite capturar movimientos mayores con menos transacciones, lo cual “reduce los costos transaccionales”【23†L255-L262】. En cambio, el day trading ofrece retroalimentación rápida pero con mayores comisiones y riesgo de deslizamiento【23†L189-L192】. El bot evaluará la relación coste/beneficio de cada horizonte (p. ej. usando simulaciones o métricas internas) para operar principalmente en modos que mantengan los gastos operativos bajos, alternando según volatilidad y liquidez del mercado.

## 2. Arquitectura de Sistemas (Stack Tecnológico)
- **Backend y API:** Servidor en Python asíncrono con **FastAPI**. FastAPI es un framework moderno de alto rendimiento para APIs en Python【26†L315-L322】, compatible con Type Hints y diseñado para producción. Su soporte nativo a *async/await* permitirá manejar eficientemente múltiples conexiones (websocket de datos de mercado, solicitudes internas, etc.) sin bloquear el loop de eventos.
- **Persistencia y migraciones:** Base de datos **PostgreSQL** para almacenar históricos de cotizaciones (ticks) y eventos, usando **SQLAlchemy** como ORM para mapear clases Python a tablas relacionales, y **Alembic** para gestionar versiones/migraciones de esquema. Esto permite modificar el esquema sin perder datos históricos y documentar cambios de modelo de datos (por ejemplo, añadir columnas de sentimiento)【29†L107-L110】【47†L167-L175】.
- **Concurrencia y mensajería:** Arquitectura distribuida con **Redis** + **Celery**. Redis actuará como broker de mensajes/pub-sub para coordinar tareas y cachear información caliente (p. ej. últimos precios); Celery gestionará tareas asíncronas (cálculo de señales, ejecución de órdenes, reentrenamiento de modelos), mejorando la escalabilidad y tolerancia a fallos.
- **Machine Learning:** Se emplearán dos enfoques: *aprendizaje continuo* para datos en streaming (librería **River**, especializada en aprendizaje online)【33†L33-L42】 y *modelos pesados* (entrenados offline) con TensorFlow. River permite entrenar modelos incrementalmente sobre flujos de datos financieros cambiantes【33†L33-L42】, ideal para adaptarse rápido a nuevos patrones. Para tareas de predicción más complejas (p.ej. redes neuronales profundas sobre secuencias de precios), se usarán modelos TensorFlow entrenados offline y desplegados para inferencia rápida.
- **Integración de mercados:** Se creará una capa de abstracción unificada. Para criptomonedas, se utilizará **CCXT**【36†L476-L484】, que soporta Binance y decenas de exchanges con una API común (consultas de libros de órdenes, cuentas, órdenes). Para el mercado local argentino, se integrarán protocolos específicos: por ejemplo, **pyRofex** permite conectarse al API REST/WebSocket de Rofex (Matba Rofex)【7†L265-L273】, y BYMA ofrece APIs de datos (precios de acciones y CEDEARs)【10†L31-L39】. De este modo, el bot puede operar tanto en mercados globales (via CCXT/Binance) como en locales (via adapters a BYMA/ROFEX).
- **Observabilidad:** Se definirá monitoreo con **Prometheus/Grafana** para métricas clave (latencias de respuesta, número de errores, uso de CPU/memoria, tasa de órdenes ejecutadas, drawdown actual, etc.). También se instrumentará trazabilidad distribuida con **OpenTelemetry** para correlacionar logs y seguimientos de transacción (por ejemplo, medir tiempos de ejecución por etapa del bot).
- **Despliegue:** Entorno **dockerizado** para el servidor y sus componentes (API, worker Celery, base de datos, exporters). Esto asegura replicabilidad local y aisla dependencias. Se usará `docker-compose` para montar servicios (API, Redis, PostgreSQL, Grafana, Prometheus) en modo local, facilitando pruebas end-to-end y cumplimiento de la latencia objetivo (250 ms en P99).

## 3. Gestión de Riesgos y Capital
- **Dimensionamiento de posición:** Se aplicará el **criterio de Kelly fraccional**. El tamaño óptimo sería $f^*=\frac{p\,(b+1)-1}{b}$ para cada estrategia, escalado por un factor conservador (0.25 dado) para reducir volatilidad【47†L167-L175】. Usar un Kelly fraccional (p.ej. Kelly al 25%) es común para “reducir la posibilidad de ruina, la volatilidad y el error de modelado”【47†L167-L175】. De este modo, el bot calcula su fracción de capital a invertir en cada señal de acuerdo a la probabilidad estimada de éxito ($p$) y la relación ganancia/pérdida esperada ($b$), limitándola luego al 25% de ese valor para no arriesgar demasiado en cada trade.
- **Restricciones de riesgo:**
  - *Drawdown máximo:* Se impondrá un límite de pérdida acumulada del 10–20% del capital, como freno global. Al llegar a ese umbral, el bot detendrá operaciones automáticamente.
  - *Stop-loss dinámico:* Cada operación llevará un stop-loss ajustable según volatilidad (p.ej. múltiplos de ATR o trailing stop). Según las buenas prácticas, todo trade debe incluir un stop-loss automático【52†L299-L303】. En el README de un bot criptográfico similar se recomienda “orden automática de stop-loss en cada posición” (1.5% por defecto)【52†L299-L303】. Además, el stop podría actualizarse dinámicamente si el mercado se mueve favorablemente.
  - *Circuit breakers:* A nivel de cuenta, se implementarán frenos automáticos. Por ejemplo, si la pérdida del día supera un umbral (p.ej. 5–10%), se suspende la apertura de nuevas posiciones y/o se cierran posiciones hacia punto de equilibrio. De hecho, una implementación existente incluye un “Circuit breaker” que detiene el trading si la pérdida diaria excede 5%【52†L299-L307】. Otro enfoque es un reset completo (kill-switch) cuando ocurre un evento extremo: p.ej. pérdida brusca por noticias (flash crash) o desincronización de mercado. El kill-switch detiene inmediatamente todas las operaciones activas. Un estudio anecdótico recomienda una “capa de límite diario duro” (p.ej. 4%) que cerró posiciones antes de que una caída violenta las terminara【49†L331-L340】.
- **Costos de transacción:** Todas las simulaciones de backtesting incluirán comisiones, spread y slippage. Ignorar estos costos inflará los resultados; de hecho, fuentes especializadas indican que las comisiones pueden “borrar entre el 30% y el 50% de las ganancias” simuladas【54†L243-L250】, y que modelar el slippage real puede reducir los retornos anuales simulados en 0,5–3%【54†L201-L202】. Por ello, el bot registrará explícitamente: comisión de Binance o mercado local, diferencia bid/ask y deslizamiento estimado (quizá basado en tamaño de orden vs. volumen), incorporándolos en cada ejecución y ajuste de performance.

## 4. Requerimientos del Documento de Salida
- **Diseño de datos:** Se propondrá un esquema optimizado para series temporales de alta frecuencia y eventos de sentimiento. Por ejemplo:
  - **Tabla Ticks:** columnas (`id`, `timestamp` (preciso, e.g. datetime con zona), `instrumento` (símbolo), `precio`, `volumen`, `bid`, `ask`…), indexada por (`instrumento`, `timestamp`) para consultas rápidas por rango temporal. Podría particionarse por símbolo y tiempo para manejar fácilmente billones de filas.
  - **Tabla Sentimiento:** columnas (`id`, `timestamp`, `activo` (opcional para qué instrumento aplica la señal), `score` (flotante), `fuente` (texto o enum: “Twitter”, “News”)). Esto registra cada señal de ánimo detectada, permitiendo cruzarla con los ticks. Indices por fecha y por activo facilitan análisis correlacional.
  - Se cuidará la normalización de esquemas (e.g. tablas auxiliares para símbolos) y el uso de formatos eficientes (tipos de datos adecuados, compresión en columna si se usa OLAP).
- **Lógica de backtesting:** Se diseñará un protocolo estricto de validación de la estrategia. Se escribirán tests unitarios con **pytest** para la lógica (por ejemplo, que las señales técnicas generen los trades esperados, que las órdenes calculen correctamente stop/profit) y para el simulador de mercado. Adicionalmente, se realizarán **simulaciones Monte Carlo**: se perturbán los datos históricos (p.ej. reordenando aleatoriamente secuencias de trades o agregando ruido) para evaluar estabilidad estadística. Estas simulaciones muestran la variación en métricas clave (retorno, drawdown máximo, tasa de éxito) y ayudan a identificar escenarios “cisne negro” (p. ej. inyectando caídas repentinas de precios). Según expertos, este tipo de análisis examina cómo podría comportarse la estrategia “ante entradas anómalas o divergentes”【60†L138-L147】. En conjunto, pytest + Monte Carlo permitirán cuantificar la robustez del bot frente a eventos extremos, midiendo métricas de drawdown, tasa de aciertos y otros indicadores de riesgo en condiciones forzadas.
- **Métrica P99 y optimización:** Se definirá la latencia como la rapidez del sistema para procesar señales y enviar órdenes. Se buscará que el *P99 latency* (tiempo al que responden el 99% de las peticiones) sea ≤ 250 ms en la ejecución local dockerizada. El p99 es un indicador de “latencia de cola” que refleja el peor 1% de las respuestas【64†L24-L32】; mantenerlo bajo significa que casi todas las solicitudes se atienden rápido, evitando tail latency crítica. Por ejemplo, muchos SLAs exigen “99% de transacciones en <250ms”【42†L138-L142】. Para lograrlo se planificará: uso de conexiones locales rápidas (sin pasar por internet), optimización de consultas (índices, caches en Redis), y profiling continuo. Se detallará un plan de caching (p.ej. almacenar último libro de órdenes en memoria) y balanceo de carga interno (p.ej. múltiples workers) para evitar cuellos de botella en la ruta crítica.
- **Flujo de trabajo de ML:** Se explicará cómo reconciliar el modelo predictivo con el desempeño real simulado. En la práctica, el modelo de ML se entrena offline con datos históricos, pero se evaluará periódicamente mediante *paper trading* en testnet (e.g. testnet de Binance) o cuentas demo de simulación. Esto implica desplegar el modelo en un entorno de simulación que capture nuevas condiciones de mercado, recopilar métricas reales (ganancias, aciertos, drawdown) y comparar con las predicciones. Con base en la performance simulado se reajustarán hiperparámetros o se re-entrenará el modelo en ciclos regulares (p.ej. mensual). En esencia, cada cierto periodo se generará un loop de feedback: predecir→ejecutar en paper trading→evaluar resultados→ajustar/re-entrenar modelo. Esta reconciliación garantiza que las versiones nuevas del modelo sigan alineadas con condiciones recientes antes de aplicarlo en real, reduciendo riesgo de *data drift*.
